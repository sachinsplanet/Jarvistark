---
name: jarvistark-intake
description: Interview the user about an app idea, propose source-linked Jarvistark requirements for human review, and hand the approved scope to architecture. Use for a new intake, a requirements review, or a change to recorded requirements.
---

Establish what the user wants before choosing how to build it. Record their own words and keep proposed requirements separate from approved scope. Use the CLI invocation from the handoff or [the bundled CLI](../jarvistark/references/cli.md). Use the [intake CLI reference](references/cli.md) for payloads, source citations, and review commands.

1. **Open the app workspace.** Use an explicit `--workspace` and run `status` to resume a recorded intake, interview, or pending review. If there is no intake, capture the user's original idea verbatim in a scratch file and record it with `init` once. If they have not described the idea, ask for it. Preserve the original as given. A later clarification or change belongs in the journal as a new answer or proposal.
2. **Ask what changes the scope.** Read the idea and recorded answers before asking a short batch of focused questions. Resolve who uses the app, who can view or change data, the main workflow, consequential failure cases, and first-release boundaries when unclear. Ask in terms of the user's experience. Record each actual question and answer with `clarify` before citing it. If the user corrects an answer, record the correction under a new question ID. If the idea needs capabilities beyond the initial accounts-and-database scope, such as multiple user roles, payments, notifications, external integrations, or real-time collaboration, agree on what the first version will cover before proposing a narrowed plan.
3. **Propose source-linked claims.** Write one reviewable requirement or constraint per claim. A user-stated claim must cite an exact passage of the original intake or a recorded answer that supports it. Check the meaning of the source as well as the reference. Put inferences, recommendations, and observed facts in separate claims with their correct origins. Leave undecided choices visible as questions. Mark a question blocking only when its answer is needed to proceed. Submit the batch through `propose` and use the actual minted IDs in review.
4. **Run the requirements review.** Show who can do what, key constraints, exclusions, and any unresolved questions. For each claim show its ID, origin, and the cited passage or answer when available. Prepare revisions when requested, with the source of the change and the ID it replaces. Open the [workspace review](../jarvistark/references/cli.md#workspace-review) and wait for the person to select and decide the claims. Chat feedback can guide the proposal. Read the ledger to confirm the final decision.
5. **Hand off approved scope.** After review, reload `status` and run `validate`. Pass the app workspace, current accepted requirements and constraints, and relevant accepted assumptions or decisions to the [architecture skill](../jarvistark-architecture/SKILL.md). List pending or deferred items separately. If an unresolved question or a missing approval affects the requested design, report it and leave that part pending. An intake-only request ends with this handoff.

Keep the CLI ledger authoritative. Keep scratch payloads out of the canonical ledger and generated plan directories.
