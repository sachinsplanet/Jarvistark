---
name: jarvistark-environment
description: Inspect an app workspace for installed, missing, or incompatible runtimes, package managers, dependencies, and local services. Use for setup guidance or to give Jarvistark architecture planning verified environment constraints and unresolved choices.
---

Inspect the user's project without changing it. Explain what they can use now, what they need to install or configure, and what still needs verification. Pass the same evidence to architecture using the [handoff format](references/handoff.md).

1. **Scope the check.** Use the app workspace and relevant subproject, not the Jarvistark checkout. Name the target you checked, usually local development in the current shell. A container, remote session, production deploy, or another contributor's machine can have different tools and package trees. Use accepted architecture decisions if available. If no stack has been selected, inspect the prerequisites the project already declares and leave new stack choices open.
2. **Read what the project expects.** Inspect the relevant setup docs, tool and runtime pins, manifests, lockfiles, workspace config, and container or CI config. Prefer the selected package manager and the lockfile for the inspected workspace. Report conflicts that affect setup instead of guessing which requirement wins. Include direct dependencies and system tools relevant to the user's goal. Read configuration templates for required key names and service requirements without reading or printing secret values.
3. **Check what is available.** Use scoped, read-only probes. Check the resolved executable, its actual version, and whether that version satisfies the project's requirement. Inspect the active environment or package manager's installed state for packages. A manifest declares a requirement and a lockfile records a resolution, so neither alone proves installation. Report a result as unverified if the inventory itself cannot run, the output is inconclusive, or a probe would run project code, fetch tools, or contact a service. Report a service separately from its client tools and configured environment variable names. See [inspection examples](references/inspection.md) for common checks.
4. **Give setup guidance.** Put missing and incompatible required items first. For each action, give the project-specific reason, working directory, installation or configuration command when known, and a check that would verify the result. Group packages satisfied by the same lockfile install. Identify optional development and deployment requirements separately. Use the existing package manager and pinned versions. When the project's own instructions are insufficient and exact install or compatibility guidance matters, verify it against primary documentation for the detected platform. This inspection recommends actions. Leave installs, upgrades, scripts, and service starts to a separately requested setup run.
5. **Hand off constraints.** Summarize the evidence-backed constraints, existing stack, and open decisions for architecture. In discovery, avoid turning a suggested stack or a local machine limitation into an approved project requirement. After architecture is approved, revisit affected entries and give exact setup steps for the selected stack. Return the structured handoff to the caller. If it needs a file, use a supplied output path or a scratch location and return the path. Keep the report outside the canonical ledger and generated plan directories.

When calling this skill within `$jarvistark`, pass the resulting discovery handoff to architecture planning before proposing stack decisions. It can also be invoked independently to answer a user's setup question.
