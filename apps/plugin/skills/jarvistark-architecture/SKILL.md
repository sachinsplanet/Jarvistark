---
name: jarvistark-architecture
description: Design a project's stack, data model, app structure, and interfaces from approved Jarvistark requirements and the environment handoff. Use to propose architecture decisions or revisions for separate human review through the Jarvistark CLI.
---

Design the smallest architecture that meets the approved requirements. Use the CLI invocation from the handoff or [the bundled CLI](../jarvistark/references/cli.md). Submit decisions using the [proposal and review reference](references/review.md).

1. **Load the approved scope.** Use the workspace and claim IDs received from the [intake skill](../jarvistark-intake/SKILL.md) if available. Run `jarvistark --workspace APP_DIR status` and read the current accepted requirements and constraints, including any accepted decisions already in force. Treat intake, proposed claims, and open questions as context. If there are no accepted requirements, return to intake and claim review before proposing architecture. On a resumed session, show any pending architecture proposals before creating replacements.
2. **Read the environment handoff.** Use the [environment skill's JSON report](../jarvistark-environment/references/handoff.md) for the same workspace, subproject, and target. Use the checked repository constraints to narrow the design and the installed/missing inventory to estimate setup work. If the report belongs to another target or setup has changed, refresh the affected observations. If it is missing, ask `$jarvistark-environment` to inspect the workspace. A missing local tool does not rule out a design by itself. Keep production decisions open when only local development is in scope.
3. **Design around the approved workflows.**
   - **User experience.** For apps with a visual interface, define the screen flows, page and component structure, content and visual direction, responsive behavior, accessibility, and loading, empty, validation, and error states. Include the actual behavior in reviewable decisions so implementation prompts can carry it forward.
   - **Stack and topology.** Choose the runtime, app shape, data store, and setup or hosting boundaries. Preserve what fits in the existing repository. For consequential choices, explain why the proposed option fits and when an alternative would make sense. Mark new prerequisites for the environment skill's setup pass.
   - **Data model.** Name entities and relationships, their identity and ownership, and the rules that protect data during updates. State where invariants are enforced. Cover atomic updates, history, migrations, or deletion behavior where the requirements make them relevant.
   - **App structure and interfaces.** Map the main workflows to modules, pages, or services. Explain who can call each important operation, where inputs are validated, how requests reach the data layer, and which existing code can be reused. Include failure behavior where it affects user-visible results.
   
   Ask only about unresolved choices that materially change the design. Keep deferred choices and assumptions visible. Verify environment or dependency compatibility when the recommendation relies on it.
4. **Propose reviewable decisions.** Use `propose` with a separate decision for each independently reviewable choice. Link every decision to its driving accepted requirements using `derives-from`. Add `depends-on` links between decisions only where one really requires another. Include the actual design and rationale in the claim text so the approved record is usable in a later session. Show decision IDs, the supporting claim IDs, alternatives that matter, and open questions. If the reviewer requests a change, propose a revision with its current source links.
5. **Hand off reviewed design.** Open the [workspace review](../jarvistark/references/cli.md#workspace-review) for the person to decide the proposed architecture claims. On resume, read `status` and run `validate`. Identify any decisions still pending that block task planning. Supply the accepted decision IDs and relevant changes in prerequisites using the handoff in the review reference. An architecture-only request ends with design review. Keep app source and generated plan files unchanged.
