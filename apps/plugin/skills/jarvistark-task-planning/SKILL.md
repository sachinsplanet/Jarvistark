---
name: jarvistark-task-planning
description: Break approved Jarvistark requirements and architecture into small implementation tasks with real dependencies and executable acceptance checks. Use to propose, revise, or review a task plan through the Jarvistark CLI.
---

Turn the accepted design into work a coding agent can implement and verify one task at a time. Stop at review and handoff. Use the CLI invocation from the handoff or [the bundled CLI](../jarvistark/references/cli.md). Submit drafts using the [task payload and review reference](references/tasks.md).

1. **Load the current plan.** Run `jarvistark --workspace APP_DIR status`. Use only current accepted requirements, constraints, and architecture decisions. Read the architecture handoff and relevant repository files to identify existing implementation and prerequisites. If a missing approval or unresolved decision changes the work, surface it and leave that part unplanned. Reuse applicable tasks and review pending drafts before proposing duplicates.
2. **Split by outcome.** Give each task one concrete outcome with a clear boundary, such as a usable migration, a protected workflow, or a behavior that needs a distinct test. Combine pieces that share an invariant and must land together. Put setup work where it actually unblocks delivery. Map each approved requirement and material design constraint to the tasks and checks that deliver it. Call out uncovered items or explicitly deferred work in the review. Keep unrelated features and proposed claims out.
3. **Choose prerequisites.** Add a dependency only when a task consumes another task's result or needs its approved behavior to be testable. Keep independent work eligible in parallel. Use current task IDs for existing prerequisites. Record new tasks in dependency order and use the task IDs returned by the CLI.
4. **Write observable acceptance checks.** Use the approved stack and an existing test runner when available. Specify the command and what it must assert, including significant failure or boundary behavior. A check can name a test file the task will create. Make the command fail if the test is missing or the required behavior fails. State what runs from the app workspace and any fixture or setup it needs. Prefer isolated data for checks. The CLI records exit status and output, so the command itself must enforce the expected behavior. Leave proposed checks unexecuted during planning.
5. **Propose and review.** Submit each draft with `task` and read `status` and `validate`. Present the task IDs, outcomes, claim coverage, prerequisites, and check commands with expected results. Open the [workspace review](../jarvistark/references/cli.md#workspace-review). For a build request, use `review --build` in this same checkpoint and pass its result to the coordinator. Explain how to revise a task before changing any accepted task definition.
6. **Confirm the handoff.** On resume, reload `status` and use `next` to check the first eligible task's context. Report which tasks await approval and which approved tasks are ready or blocked, with reasons. Give the implementation agent the verified CLI invocation and explicit workspace path. A validation pass alone does not mean tasks were approved or checks passed. Leave `start`, implementation, and check execution for the implementation workflow.

Include the [execution contract](../jarvistark-prompts/references/execution.md) in each new task. Carry the approved design and checked environment findings into that contract, with precise interfaces, existing files to read, and expected artifacts. Run `plan` to check requirement coverage and execution findings, then hand approved work to the [prompt skill](../jarvistark-prompts/SKILL.md).

Use the app workspace explicitly. Keep scratch payloads outside canonical ledger and generated plan paths.
